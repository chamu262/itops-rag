IT Operations : Identity Architecture: Entra ID, Google Workspace Federation and App SSO Standard

Created by Identity & Access, last modified on Oct 12, 2026

Overview

Microsoft Entra ID is Kestrel's single identity provider. Every person has one identity, first.last@kestrelcloud.example, created from the HR system and used for laptops, Google Workspace, MeshGate and SaaS applications. No application keeps its own password database for staff unless listed as an exception in the SaaS register.

Identity lifecycle

  1. HR system is the source of truth. Inbound provisioning creates and updates Entra users hourly: department, office, manager, start and end dates.
  2. Entra ID holds users, dynamic groups (SG-Office-*, SG-Dept-*), authentication methods and Conditional Access.
  3. Google Workspace receives users and groups via Entra SCIM provisioning (every 40 minutes) and accepts SAML sign-in from Entra (profile Entra-KC, see VND-004).
  4. SaaS apps are connected using SAML 2.0 or OIDC, plus SCIM when the vendor supports it (CF-006).
  5. Devices: Macs use Platform SSO against Entra; Windows devices are Entra joined. Device compliance from Jamf and Intune is written to the Entra device object.

Google Workspace federation

Google is a service provider only. Passwords are never synchronised to Google. Two super admin accounts in OU /IT/SSO-Bypass sign in to Google directly with hardware keys for recovery. The SAML signing certificate is the single point of failure for Google sign-in; rotation is a planned change with a runbook (RB-GWS-002).

App SSO onboarding standard

RequirementStandard
ProtocolOIDC preferred for new apps; SAML 2.0 accepted. WS-Fed and password vaulting are not accepted.
SigningSHA-256; SAML response or assertion signed; certificate lifetime 3 years; notification email it-identity@kestrelcloud.example
NameID / subjectUPN (email format). Never employee number or object ID unless the vendor requires it.
AssignmentAssignment required = Yes; access through group SG-App-<AppName>, never individual users
ProvisioningSCIM 2.0 where available, with deprovisioning tested. Otherwise app must honour SSO-only login and be in the manual leaver list (RB-GEN-002).
Local loginDisabled for all users except one vendor break-glass account stored in the Security Operations vault
Conditional AccessCovered by the baseline policies (CA-001 to CA-040); apps with customer data are in scope of CA-020 compliant device
OwnerA named business owner team and Identity & Access as technical owner

Administrative access

  • Admin roles are assigned through Privileged Identity Management (PIM) as eligible, with activation up to 8 hours and justification.
  • Admins use separate adm- accounts with FIDO2 keys.
  • Two emergency access accounts exist (procedure restricted to Security Operations).
